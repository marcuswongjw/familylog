# P1 fixes — 15 October 2026

This change addresses findings 1–4 in `code-review-2026-10-14.md`. It does not claim to fix the remaining P2 findings or merge any historical duplicate financial records.

## Expense identity and deletion

Expenses now have an immutable ID in column G, an operation fingerprint in H, and deletion status in I. Existing operation IDs are retained. Rows without IDs receive UUIDs in a single batch under the parent-service lock on first read. New manual, recurring and bank-approved expenses receive IDs immediately.

The client deletes by ID. Old row-number-only requests and header targets are rejected with a refresh message. Deletion marks the row Deleted rather than shifting neighboring records. Dashboard totals/history, budgets, budget alerts and scheduled expense reports exclude these rows. Stable destination records remain available for approval retry recovery.

## Bank approval recovery

An approved expense uses a deterministic ID derived from the signed pending-transaction ID. If appending succeeds but its response or pending retirement is lost, retrying finds that same expense and finishes retirement without another append. An already-retired pending transaction with a matching saved expense returns confirmation. Deleting a partially approved expense does not cause the approval retry to resurrect it. Approval signatures and parent-only application actions remain enforced.

This prevents new duplicates caused by this approval path; existing duplicates are not automatically merged because matching amounts/dates alone cannot establish that two legitimate transactions are the same.

## Calendar occurrence identity and moves

Calendar reads now use the paginated Google Calendar REST list with singleEvents=true. Recurring occurrences use their stable REST instance IDs, exposed as instance:<id>, with the shared series iCalUID retained separately. One-off events retain their legacy iCalUID for compatibility with existing manual and school links. School-event restrictions and member tags/mirror targeting are preserved.

Old requests attempting to change a recurring series through a shared iCalUID are rejected until the client refreshes. Instance updates/deletes resolve exactly one REST resource; conditional requests detect intervening changes. One-off legacy requests still use CalendarApp, with an explicit recurring-event guard.

Timed moves retain original elapsed duration and seconds. All-day moves retain the exclusive end-date span using the supported all-day API. Preparation sources are keyed by occurrence, so one week cannot overwrite or suppress another. Existing legacy preparation migrates only to an occurrence matching its stored due date; task IDs, statuses, reward links and completion history are retained.

The health check verifies REST Calendar access in addition to native Calendar/Sheets access. It returns no household records.

## Verification and release

186 Node tests and 19 browser tests pass locally. The test harness now models the Apps Script Singapore timezone even on UTC CI hosts, Calendar REST expansion/pagination/mutations, and the supported native all-day methods. New cases cover stale parent sessions, Undo, missing IDs, bank append/retirement failures, recurrence identity, packing-history migration, all-day spans, overnight/multi-day duration, concurrent edits and failed calendar pages.

Deploy the family service first, verify its read-only readiness check, then the parent service and the reviewed static client release (v39). The Calendar advanced service is declared in the manifest to enable the REST API in Apps Script’s default Google project. The first rollout failed its API check and was restored to the previous version; the configured replacement passed on an isolated deployment before promotion. No additional Google OAuth scopes or Firebase rules are required. Older cached expense controls may need a refresh; unsafe row-number deletion does not fall back to guessing.

Rollback must retain expense Status filtering and the ID-based delete contract. Rolling the entire backend back to a version that does not understand Deleted rows would count retired expenses again; prefer a forward repair or retain this data contract in a targeted rollback.
